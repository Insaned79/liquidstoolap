# Надёжность хранилища

Liquid Stoolap собирает Stoolap 0.4.0 из commit
`7e6634ba8447f33ae99aefb99693459cd691394a` с проверенным патчем
`patches/stoolap-0.4.0-liquidstoolap.patch`. Релизная сборка не зависит от
изменяемой ветки Stoolap `main`.

## Гарантии восстановления

- Volume записывается во временный файл, синхронизируется, повторно читается и
  проверяется по CRC до переименования и публикации в manifest таблицы.
- Заголовок и индекс блоков сверяются с физическим размером файла до выделения
  памяти по содержащимся в них значениям.
- При восстановлении WAL проигрывается до окончательной проверки целостности,
  поэтому подтверждённые `DROP TABLE` и `TRUNCATE TABLE` корректно отменяют
  старые ссылки на volumes.
- После WAL replay каждый segment, оставшийся в действующем manifest, обязан
  существовать и пройти проверку формата и CRC. Иначе открытие завершается
  ошибкой `storage integrity error`; частичные данные молча не выдаются.
- `DROP TABLE` после надёжной записи в WAL удаляет весь каталог хранилища
  таблицы. `TRUNCATE TABLE` публикует пустой manifest до удаления старых volumes.
- Одна compaction загружает не более 16 входных volumes, поэтому её рабочая
  память ограничена даже после длительного накопления очереди.

Физическое повреждение носителя невозможно исправить по единственной копии.
Ошибка целостности требует восстановления из проверенного бэкапа или реплики.
Отказ от частичного запуска не позволяет клиентам принять неполный результат
запроса за корректные данные.

## Проверка

Исправленный движок проходит принятый upstream цикл:

```bash
cargo fmt --all -- --check
cargo test --test volume_checkpoint_test
cargo test --test durability_test
cargo test
```

Regression-тесты покрывают отсутствующие и повреждённые manifest-volumes,
ограниченную compaction, незавершённую публикацию volume, повреждение manifest,
WAL recovery и безопасный порядок операций `DROP`/`TRUNCATE`.
